## Q1. What do Anthropic's own materials offer for post-task quality raising?

### Takeaway
Anthropic ships four distinct mechanisms: a prose recipe (verify, then optionally add an adversarial subagent review), a deterministic gate (Stop hook, which can force the agent to continue), a model-judged gate (`/goal` and prompt/agent Stop hooks), and bundled commands (`/code-review`, `/simplify`, `/verify`). The docs explicitly warn that a reviewer told to find gaps will report some even when the work is sound, and that chasing every finding causes over-engineering. No first-party material provides a task-type-agnostic "raise the bar" pass for non-code work.

### Cited Findings
- **A Stop hook can force the agent to continue.** `decision: "block"` with a required `reason` "prevents Claude from stopping"; exiting 2 does the same and the stderr text becomes the reason. `hookSpecificOutput.additionalContext` also continues the conversation, labelled "Stop hook feedback" instead of an error. `SubagentStop` supports the same. — [Hooks reference, Stop decision control](https://code.claude.com/docs/en/hooks.md) (HIGH, read in full from the downloaded markdown)
- **There is a built-in loop cap.** "Claude Code applies an 8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn. The count ... resets each time Claude calls a tool." Raise with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. The input field `stop_hook_active` is true when already continuing, so scripts can avoid blocking on a condition that never resolves. — [Hooks reference, Stop input](https://code.claude.com/docs/en/hooks.md) (HIGH)
- **Stop hooks can be model-judged.** `type: "prompt"` (single-turn model check) and `type: "agent"` (spawns a subagent with tools, up to 50 tool-use turns, experimental). For Stop and SubagentStop, `ok:false` feeds `reason` back so Claude keeps working, unless the prompt hook also returns `"impossible": true`, which lets the stop through. — [Hooks guide: prompt-based hooks](https://code.claude.com/docs/en/hooks-guide.md#prompt-based-hooks), [agent-based hooks](https://code.claude.com/docs/en/hooks-guide.md#agent-based-hooks) (HIGH)
- **`/goal` is a session-scoped prompt-based Stop hook.** After each turn a "small fast model" judges the condition against what the transcript already shows; it "does not call tools". Verdicts: met, not met, impossible. Stalls (no tool use for several turns) stop the loop and return control. Bound it by putting "or stop after 20 turns" in the condition. — [/goal docs](https://code.claude.com/docs/en/goal.md) (HIGH)
- **Best-practices page, verification.** "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available." It lists four gate strengths: ask in the prompt; `/goal`; a Stop hook "as a deterministic gate"; a "verification subagent" so "the agent doing the work isn't the one grading it". It also says "Have Claude show evidence rather than asserting success". — [Best practices: Give Claude a way to verify its work](https://code.claude.com/docs/en/best-practices) (HIGH)
- **Best-practices page, adversarial review, with an explicit anti-over-polish warning.** "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen. Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional." A fresh-context subagent "sees only the diff and the criteria you give it, not the reasoning that produced the change". — [Best practices: Add an adversarial review step](https://code.claude.com/docs/en/best-practices) (HIGH)
- **Best-practices page, Writer/Reviewer.** "A fresh context improves code review since Claude won't be biased toward code it just wrote." — [Best practices](https://code.claude.com/docs/en/best-practices) (HIGH)
- **Best-practices page on failure patterns.** "The trust-then-verify gap ... If you can't verify it, don't ship it." Also: after two failed corrections, `/clear` and rewrite the prompt. — [Best practices: Avoid common failure patterns](https://code.claude.com/docs/en/best-practices) (HIGH)
- **Bundled commands.** `/code-review [low..max|ultra] [--fix]` reviews the diff "for correctness bugs"; runs as a forked/background subagent with its own context; at `low` it "reports the findings it's most confident in, so you see fewer false positives", from `medium` through `max` it broadens coverage. `/simplify` runs four parallel review agents (reuse, simplification, efficiency, right level of abstraction) and "doesn't look for correctness bugs". `/verify` builds and runs the app and observes the result "rather than relying on tests or type checks". `/loop` repeats a prompt on an interval or self-paces. — [Commands](https://code.claude.com/docs/en/commands.md), [Review locally with /code-review](https://code.claude.com/docs/en/code-review-local) (HIGH)
- **How skill descriptions trigger.** "Claude uses [description] to decide when to apply the skill." `description` + `when_to_use` are truncated at 1,536 characters in the skill listing. `disable-model-invocation: true` removes the skill from automatic triggering. So a post-task skill fires only if the model judges the description matches; there is no "task finished" skill event. — [Skills docs, frontmatter reference](https://code.claude.com/docs/en/skills.md) (HIGH)
- **Evaluator-optimizer pattern.** "One LLM call generates a response while another provides evaluation and feedback in a loop." Fit signals: "clear evaluation criteria" and "iterative refinement provides measurable value". The post gives no iteration cap for this workflow; its general advice is "stopping conditions (such as a maximum number of iterations)" and that agents should "gain 'ground truth' from the environment at each step". — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (HIGH)
- **First-party plugin: `ralph-loop`.** A Stop hook re-feeds the same prompt until the model emits `<promise>TEXT</promise>` matching a configured promise, or `max_iterations` is hit. With no promise set it "runs infinitely" (`stop-hook.sh:176`); the iteration check is skipped when `max_iterations` is 0 (`stop-hook.sh:61`). — local `/Users/firegroup/.claude/plugins/marketplaces/claude-plugins-official/plugins/ralph-loop/hooks/stop-hook.sh` (HIGH, read in full)
- **First-party plugin: `code-review` command.** Step 4 launches 5 parallel Sonnet agents (CLAUDE.md compliance, shallow bug scan, git blame, prior PR comments, code comments); step 5 scores each issue 0-100 with Haiku agents using a rubric; step 6 "Filter out any issues with a score less than 80". It lists false-positive classes (pre-existing, linter-catchable, pedantic nitpicks, general quality issues unless required by CLAUDE.md). — local `.../claude-plugins-official/plugins/code-review/commands/code-review.md` (HIGH, first 40 lines read)
- **First-party plugins: `pr-review-toolkit` and `code-simplifier`.** pr-review-toolkit bundles 6 narrow agents (comment-analyzer, pr-test-analyzer, silent-failure-hunter, type-design-analyzer, code-reviewer, code-simplifier). Its `code-reviewer.md` lists "proactive review of newly-written code ... before declaring a task done" as an invocation scenario. `code-simplifier` is a single agent with the rule "Never change what the code does - only how it does it". — local `.../plugins/pr-review-toolkit/README.md`, `agents/code-reviewer.md:3,15`, `code-simplifier/agents/code-simplifier.md` (HIGH, heads read)

### Inferences
- Anthropic's own guidance already states the central design constraint for a new skill: an independent reviewer must be told what counts as a finding, otherwise it manufactures findings and drives over-engineering. (MEDIUM, inferred from the quoted paragraph)
- The only deterministic "after task" trigger in Claude Code is the Stop hook (plus `/goal`, which is a Stop hook wrapper). A skill alone cannot guarantee a post-task pass; it depends on model judgment of its description. (MEDIUM, inferred from skills.md frontmatter table plus hooks reference)
- Built-in coverage splits cleanly: `/code-review` = correctness bugs, `/simplify` = cleanup, `/verify` = does it run, `/goal` = keep going to a stated end state. Nothing built in judges "is this the best version of the deliverable" or works on non-diff artifacts. (MEDIUM; verified against the command list, absence claim limited to the docs pages I read)

### Gaps
- I did not read the `/simplify` or `/code-review` skill bodies (bundled, not on disk in a location I found), only the docs descriptions.
- The Claude Code docs give no effectiveness numbers for any of these mechanisms; the "8-consecutive-continuation cap" rationale is not explained beyond loop protection.
- Whether the `Stop` hook `type: "agent"` is stable is unclear: docs label it experimental.

### Inferences

## Q3. Which mechanisms do they use, and which have stopping rules or anti-over-polish guards?

### Takeaway
Seven mechanism families appear. Prose instruction and checklists dominate and are unenforced; hooks are the only way to force a post-task pass, and every hook-based loop I read relies on a cap or a model judge to terminate. Explicit anti-over-polish guards exist in only a minority: fixed round caps (most common), "not perfect is shippable" statements (robisson, aio-code-review), a no-op-is-valid rule (aio-anti-slop), confidence thresholds (official code-review), and Anthropic's reviewer-prompt advice. A marginal-return stop ("stop when a round adds nothing new") appears in exactly one place I read: aio-code-review's workflow.

### Cited Findings

### Inferences
- Caps are about runtime safety (do not loop forever), not about quality economics. The only marginal-return rule found (stop when a round yields no new findings) is the aio-code-review `dry` counter, and it applies to finding discovery, not to deciding whether to fix. (MEDIUM)
- The common fix-side guard is a human-or-rule filter on which findings to act on (YAGNI check in receiving-code-review, NIT never blocks, threshold 80, Anthropic's "treat the rest as optional"). A new skill needs a triage rule for "act / note / drop" more than it needs a round cap. (MEDIUM)
- A hook can force continuation but cannot supply what "better" means; every hook-based loop I read needs the criterion supplied externally (a promise string, a goal condition, a test). (MEDIUM)

## Q4. Gap analysis: what is not covered by anything found

### Takeaway
Seven gaps survive the survey. The largest: nothing found is a task-type-agnostic pass (code, docs, plans, analysis) that derives "done" criteria from the user's request, uses an independence level matched to risk, applies the highest-value fix rather than only reporting, and stops on a marginal-return rule. Absence claims are bounded by the 26 candidates and the searches listed in the coverage statement.

### Cited Findings
Each gap below states the evidence from the catalog; "no counterexample found" means none of the 26 candidates contradicts it.

- **G1. No task-type-agnostic improvement pass.** The reviewer-side or diff-bound members are rows 1, 3, 5, 7, 8, 9, 14, 16, 26 (code or diff only). The prose-capable ones are aio-anti-slop (prose style only, `SKILL.md:27` "a style pass, not a content edit") and self-eval/reflect (score or redirect, do not revise the artifact). No counterexample found. (HIGH for the 26 examined, MEDIUM ecosystem-wide)
- **G2. Score-or-review versus improve.** self-eval produces a number and no revision; reviewers produce findings and hand fixing to the author; `code-polish`, `/simplify`, anti-slop fix but only along fixed axes (comments, reuse/efficiency, AI tells). No skill examined takes the finished deliverable, identifies the single highest-leverage weakness against the user's goal, and fixes it. Nearest: `/code-review --fix` for bugs only. (MEDIUM)
- **G3. Criteria are fixed, not derived from the request.** All rubrics are fixed lists (5, 8, 12 items). Anthropic's best practices tells the human to write "the plan to check it against, and what counts as a finding" in the prompt; the only skill that automates criteria creation is npow `loop-until-done` (PRD planner + falsifiability judge), which is Temporal-backed, 5 stars, and lists unfinished features as TODOs in its own file. A lightweight "restate the ask as testable done-criteria, then grade" step is absent. (MEDIUM)
- **G4. Independence of the critic is not graded by risk or task type.** The ecosystem offers three levels separately: same-context self-review (self-eval, vibe-coding-os, anti-slop self-hunt), fresh subagent (requesting-code-review, `/code-review`), different vendor (zooltd debate). Only athola's module argues that self-verification is insufficient for high-stakes work, and aio-anti-slop admits "You cannot reliably see your own slop" (`SKILL.md:25`) and compensates with mechanical detection. No skill selects the level by stakes. (MEDIUM)
- **G5. Calibration and learning from the pass's own findings.** self-eval calibrates scores across sessions; robisson captures recurring review findings (requires the `.bla` framework); claude-reflect learns from user corrections, not from self-review findings. No skill examined measures whether a pass changed the outcome (before/after, hit rate of accepted findings). Bugbot's resolution-rate idea is the only outcome-based metric found, and it is vendor-internal. (MEDIUM)
- **G6. Marginal-return stopping and a triage rule are not first-class.** Caps and "not perfect" statements exist, but no skill states an explicit rule for when to stop polishing (for example, stop when the best remaining finding is below a materiality line) alongside an act / note / drop triage. Anthropic's reviewer-prompt advice is the closest. Risk is documented: iterating can degrade results (Shukla et al.). The tension with the user's word "perfectize" is real: aio-code-review's Standard states "There is no 'perfect' code, only 'better' code" (`SKILL.md:54`), and the seed says Ship It does not mean perfect. (MEDIUM; Shukla evidence is domain-specific to code security)
- **G7. Trigger reliability for "after the task".** Skills trigger on description match; aio-code-review's trigger words are all review-intent ("review pr", "lgtm", `SKILL.md:4`), none are author-side completion phrases ("before I say done", "I just finished"). The only deterministic post-task trigger is a Stop hook, and the docs show `additionalContext` for exactly "Please run the test suite before finishing" ([hooks reference](https://code.claude.com/docs/en/hooks.md)). I found no quality skill shipping a paired Stop-hook nudge. (MEDIUM; absence limited to items read)

### Inferences
- A distinct niche exists between `/code-review` (find bugs in a diff), `/simplify` (cleanup), `aio-anti-slop` (tells), and `verification-before-completion` (evidence for claims): an author-side, artifact-agnostic "second look" that (a) restates the ask as criteria, (b) names the weakest part, (c) picks critic independence by stakes, (d) applies the fix, (e) stops by materiality. This is a hypothesis for the designer, not a finding. (LOW-MEDIUM)
- Designing around the Anthropic caveat (reviewers manufacture findings) is more important than the round cap: the skill's critic prompt should define what counts as a finding. (MEDIUM)

### Gaps
- Cannot rule out private or unindexed skills; the survey cannot prove a negative across the whole ecosystem.
- I did not test any skill's behavior by running it; all descriptions come from reading the instructions, so claimed behavior (for example "cannot override the matrix") is what the text asks for, not what the model does.
