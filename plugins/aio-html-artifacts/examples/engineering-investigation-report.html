The successful path crosses three boundaries.

The banner and OAuth callback only establish permission. Delivery becomes reliable when the callback also reaches the installer that owns dispute subscriptions.

1 · ConsentBanner opens OAuth only for flagged shops missing the scope.
→
2 · PersistCallback stores the granted scope in shops.scopes.
→
3 · RecoverValidation invokes the legacy order installer, not the dispute owner.

The decisive branch is visible in six lines.

01

Banner eligibility survives an abandoned OAuth flow

The predicate reads persisted scopes. If the callback never saves the new value, the predicate remains true and the user sees the banner again.

web/app/disputes/banner.ts · lines 41–46 · fictional example const granted = new Set(shop.scopes.split(",")); const missing = !granted.has(DISPUTE_SCOPE); return shop.flags.disputes && missing;
Why this answers the questionThe database remains authoritative. Abandoning OAuth produces no persisted scope, so missing stays true.
02

Recovery invokes only the order installer

The callback publishes a validation command, but the consumer hard-codes one Lambda target. No SNS fan-out or second SQS consumer appears in the inspected topology.

workers/validate-webhooks.ts · lines 72–80 · fictional example if (shop.active && shop.scopes.includes(requiredScope)) { await lambda.invoke({ FunctionName: "orders-install-webhooks-prod", Payload: JSON.stringify({ shopId: shop.id }), }); }
The gapThe condition is right, but the only named target owns order topics. Permission recovery does not imply dispute subscription recovery.

This fails silently, not immediately.

User completes the second OAuth attempt.

The scope is saved, so the banner correctly disappears.

The validation message is consumed successfully.

Queue health remains green because the consumer and Lambda invocation both succeed.

The wrong installer owns the recovery action.

The dispute topic is never registered; there is no failing call to alarm on.

Missing events surface later as data drift.

Inferred The first visible symptom is stale dispute state, not an authorization error.

Close the loop at the owner boundary.

Make one component authoritative for dispute webhook reconciliation and invoke it idempotently after scope persistence. Then observe the subscription result, not merely the queue delivery.
